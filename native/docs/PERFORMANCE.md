# 最適化と測定

## 実装済みの構造

- BFSを連続配列の距離表とキューへ移植。文字列座標キーを検索しない。8方向の走査順と同距離順を維持する。
- モデルを原本から一度抽出し、GPUバッファを再利用。毎フレームのモデル頂点生成・全モデル再転送を行わない。
- 地形のGPUバッファはフロアまたは壁の向きを変更した時に再構築する。
- 文字をGPUテクスチャへキャッシュし、古いものから128件を目安に破棄。同一フレームで参照するテクスチャを途中で破棄しない。
- UI頂点/バッチ/描画インスタンスのCPU配列を再利用。UIの転送用バッファも再利用し、1回のコピーで送る。
- VSyncを使用。バックグラウンドでは描画と音声を休止。
- Releaseでは利用できる場合にIPO/LTOを有効化。fast-mathを使用しない。

これは構造上の変更です。元HTMLに対して何倍高速になったという比較結果はまだありません。
描画の真のインスタンシングは未実装で、表示するモデルごとに描画要求を発行します。

## 測定の仕組み

検証アプリは直近240サンプルの平均フレーム時間とp95を計算し、0.5秒ごとに表示します。
描画要求数・CPU側で送信したバイト数・文字キャッシュ数も計数し、
--smoke-frames=8で終了時にログへ出します。

CPU区間の壁時計時間にはGPU待ちが含まれ得ます。CPU使用率やGPU時間ではありません。
GPU使用率・GPUタイムスタンプ・全プロセスRSS・熱/電力の取得は未実装です。

ヘッドレスの地形生成は次で測定します。

~~~sh
cmake --build build-core --config Release --target profile-map
~~~

12回のウォームアップ後、600フロアの生成時間の平均/p95と、
保持する配列のcapacityから計算したバイト数をJSONへ出します。
一時BFS領域、アロケーターの管理領域、Data、GPUメモリ、プロセス全体の消費量は含みません。
CIマシンでの数字をユーザー端末の性能として扱わないでください。

## 確認済みの範囲

Linux CIの最初のVulkan起動試験:
8フレーム、終了フレーム32描画要求、累計5,043,548バイト送信、文字キャッシュ18件。
初期アセット転送も含むため、フレーム当たりの転送量として使えません。
短い起動試験であり、FPSの達成判定や安定性試験ではありません。

PC 60〜120FPS、スマートフォン60FPSは目標です。達成済みの測定結果はありません。

## 本体移植後に進める項目

行動計画と経路探索の再計算削減、領域再利用、真のインスタンシング、
可視範囲での描画選別の改善、解像度の自動調整、アイドル時の低消費電力化。
同じシード/操作列/各フェーズの状態とイベントを照合した上で適用します。

## 地形生成のCI測定

試験済みコード: a8a187dd1fb67a1b09c3f38c4549babf65b8c37c。
12回のウォームアップ後に600回を測定。1〜6Fを循環し、固定した乱数系列を使用した。

|CI環境|平均|p95|保持ベクターの容量上限|
|---|---:|---:|---:|
|Windows / MSVC|38.168 µs|48.700 µs|2,907 bytes|
|Linux / GCC|27.770 µs|34.511 µs|2,883 bytes|

両環境のrng_checksumは1,300,983,508,890で一致した。
容量はFloorの配列領域の見積もりであり、BFSなどの一時配列、データ全体、
アロケーター管理領域、プロセスRSS、GPUメモリを含まない。
異なるCIマシン同士の数字なので、OSやコンパイラーの優劣の比較には使用できない。
元HTML版との速度比較やゲーム中のFPSを示す結果でもない。
