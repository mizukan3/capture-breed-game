## 実装から確認した仕様

- 通常階は29×29、最大8部屋、最初の部屋は(3,3),9×8。開始位置(7,7)。6Fは21×21のボス部屋、開始(7,10)、出口(16,10)。
- 接続順、BFSの8方向順、同距離時の安定した並び、乱数呼び出し回数が配置結果に影響する。
- xorshift32。保存rngを符号なし32ビットとして扱い、2^32で割る。C++では式の評価順に頼らず1回ずつ乱数を取得する。
- 斜め移動と視線は壁角を通過しない。探索者の視界は半径7の円内＋supercover視線。
- 手番は探索者→敵→仲間→維持処理。陣営内は回避率降順・乱数同順位判定。攻撃/技を先に処理し、移動予約と連鎖解決で同時移動する。
- 基本ダメージはmax(1,floor(1+攻撃²/(攻撃+防御)))。命中、ガード、会心の順で乱数判定。会心と凍結は各々1.5倍して各段階で切り捨てる。ガード率0でも原本は判定乱数を消費する。
- モンスター成長は種別指数付き補間、探索者は指数1.2。20Lv単位の回避・命中・会心増分を維持する。
- 通常種はHP半分以下、ドンテングは恐怖が捕獲条件。条件を満たせば捕獲は確定。距離2・見通し・収容枠・資源を検査し、成功時のみクリスタル1個消費する。
- 通常アイテム20枠、小カプセル1個/5体、同行3体、倉庫50枠。通常帰還時は通常品の半分を切り上げ個数でランダムに失う。
- 原本の配合は解禁のみ。レシピ/子種決定/継承は準備中。罠モデル・SE・説明はあるが現在のダンジョンの生成配列は空、発動APIも無効。これを移植側の実装完了と取り違えない。
- 3Dは低ポリゴンを手続き生成。床壁・キャラクター・装備・アイテムに外部画像を使わない。faviconだけが埋め込みSVG。__soundAssetsは空で、主にWebAudio合成が使われる。
- 保存は5スロット。UTF-16単位FNV-1aチェックサム、主/バックアップ/ステージング、連番、書き戻し検査、Capacitor側の退避がある。

## 段階ごとの実装計画

1. 解析: 原本識別・21モジュールの対応表・データ抽出。添付版との差分は確認待ちとして残す。
2. 基盤: CMake/C++20、純粋なcore、SDL3 GPU、文字/画像/音声、タッチとキーボード、ライフサイクル。Windows/LinuxのCIで実ビルドを行う。
3. 本体: 探索とターン、敵/仲間の行動計画と同時移動、状態と特技、捕獲/編成/所持品/装備/育成/融合/帰還、全メニュー/図鑑/演出/保存。原本にない配合レシピを推測で作らない。
4. 照合: 同じ乱数状態と操作列を原本JSとC++へ入力し、各フェーズの状態・イベント・乱数消費・保存を比較する。
5. 最適化: 正しい結果を固定後に地形/モデルGPU常駐、共有メッシュ/インスタンス、文字キャッシュ、BFS領域再利用。CPU時間・メモリ・GPU転送量を計測し、差分を照合する。
6. 各環境: Windows配布、Android Gradle/JNI、iOS Xcode/署名。ビルド確認と実機起動確認を別々に管理する。Vulkanを使えないAndroid向けGLESフォールバックもこの段階で実装/検証する。
